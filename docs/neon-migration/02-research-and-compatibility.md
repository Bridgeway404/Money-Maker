## ⛔ Blocking incompatibility — Neon Auth requires Next.js ≥ 16

`@neondatabase/auth` declares a hard peer dependency on Next.js 16:

- `0.1.0-beta.1` (2025-12-07) → `next: ^16.0.6`
- every subsequent release through `0.4.2-beta` (2026-06) → `next: >=16.0.6` / `>=16.0.0`

**No published version supports Next.js 14 or 15 via peer range.** This
repository is on **Next.js 14.2.35** (kept deliberately in Phase 1; the major
upgrade was assigned to Phase 1.5). Additional confirmation from the official
Next.js guide (`packages/auth/NEXT-JS.md`):

- the middleware pattern is `proxy.ts` (`export default auth.middleware(...)`)
  — `proxy.ts` is a **Next 16 convention** (this repo uses `middleware.ts`);
- the guide targets Next 15+/16 App Router semantics (async request APIs).

`npm install` under npm 10 enforces peer ranges: adding `@neondatabase/auth`
(or `@neondatabase/neon-js`, which depends on it) to this repo **fails
`npm ci`**. Forcing it with `--legacy-peer-deps` would install anyway and then
fail at runtime on Next-16-only APIs — that is exactly the "silently combine
the migration with a major framework upgrade" failure mode this task prohibits.

### Decision (per task instruction: stop and report, don't silently combine)

- **Blocked in this PR:** Neon Auth replacement (§6), invite-only signup UI,
  member-scoped Data API query conversion (§13 client paths), and therefore
  the removal of Supabase from the running app. The app keeps building and its
  112 tests keep passing; Supabase remains the runtime auth until the cutover.
- **Delivered in this PR (framework-independent):** full Supabase audit;
  architecture decision; complete Drizzle schema + SQL migrations with
  default-deny RLS for the entire IOP data model; migration safety guard;
  mock-only seed; env-gated database-backed RLS test suite; documentation and
  manual steps.
- **Unblock path:** Phase 1.5 (already planned) upgrades Next.js to a patched
  major ≥ 16. The auth + query cutover then proceeds against this PR's schema
  with no rework — the auth module shape, env vars, and RLS policies below are
  written against the verified current SDK.

## Verified Neon Auth Next.js pattern (for the post-1.5 cutover)

From the official NEXT-JS.md — recorded so the cutover is mechanical:

```ts
// src/lib/auth/server.ts
import { createNeonAuth } from '@neondatabase/auth/next';

export const auth = createNeonAuth({
  baseUrl: process.env.NEON_AUTH_BASE_URL!,
  cookies: { secret: process.env.NEON_AUTH_COOKIE_SECRET! }, // ≥ 32 chars, server-only
});
```

- Route handler: `app/api/auth/[...path]/route.ts` → `export const { GET, POST } = auth.handler()`
- Middleware (Next 16 `proxy.ts`): `export default auth.middleware({ loginUrl: '/login' })`
- Server components / route handlers: `const { data: session } = await auth.getSession()`
  (components using it must render dynamically — this repo already forces
  dynamic rendering on protected pages)
- Browser: `createAuthClient(NEXT_PUBLIC_NEON_AUTH_URL)`; the
  `SupabaseAuthAdapter()` option exposes `signInWithPassword` / `signUp` /
  `signOut` / `getSession` / `resetPasswordForEmail` — a near drop-in for the
  three files that call Supabase auth in the browser today.

## Verified environment-variable names

| Variable | Side | Source of truth |
|---|---|---|
| `DATABASE_URL` | server-only | Created by the Neon↔Vercel integration (pooled; runtime queries) |
| `DATABASE_URL_UNPOOLED` | server-only | Created by the integration (direct; **Drizzle migrations only**) |
| `NEON_AUTH_BASE_URL` | server-only | Neon Auth (console → Auth) |
| `NEON_AUTH_COOKIE_SECRET` | server-only, ≥ 32 chars | Generated by Michael (see manual steps) |
| `NEXT_PUBLIC_NEON_AUTH_URL` | browser-safe | Same URL as base URL; used by `createAuthClient` |
| `NEON_DATA_API_URL` / `NEXT_PUBLIC_NEON_DATA_API_URL` | browser-safe URL | Console → Data API (format `https://ep-….apirest.….neon.build/<db>/rest/v1`) |

Neither `DATABASE_URL` nor `DATABASE_URL_UNPOOLED` may ever be imported into
browser code; a bundle test enforces this (see `drizzle/__tests__`).

**Environment inspection limits:** this workspace has no Vercel credentials and
no `.vercel`/`.netlify` metadata, so the variables the integration actually
created in the Vercel project could not be enumerated from here.
`DATABASE_URL` and `DATABASE_URL_UNPOOLED` are confirmed by Michael's report;
the Neon Auth / Data API variables do **not** exist yet unless those features
were already enabled in the console (manual steps, doc 05).

## Compatibility summary

| Question | Answer |
|---|---|
| Can Drizzle + `@neondatabase/serverless` be adopted on Next 14 now? | **Yes** — framework-independent; installed in this PR |
| Can migrations/schema/RLS land before the Next upgrade? | **Yes** — they never import Next |
| Can Neon Auth land before the Next upgrade? | **No** — peer `next >= 16` on every published version |
| Can the Data API client (`neon-js`) land before the upgrade? | **No** — it depends on `@neondatabase/auth`, same peer conflict |
| Is Neon Auth GA? | **No** — all versions are `-beta`; acceptable for an 8-member internal tool, but worth noting before production cutover |
| Node version | Repo CI on Node 20 satisfies `@neondatabase/serverless` (≥ 19) |
| Preview branches | The Vercel integration creates an isolated Neon branch per preview deployment with branch-specific `DATABASE_URL*`; migrations in CI/preview must target that branch, never production (enforced by `scripts/migrate.mjs` guard) |
